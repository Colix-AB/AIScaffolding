# Environment Variables — The Dev Template and the Production Provisioning Stay in Lockstep

The repo ships an environment template at `<path/to/.env.example>` for **local development**, and provisions **staging/production** through `<infrastructure-as-code | secret manager | platform config>`.

A fresh **dev** machine copies the template and runs with the documented placeholders. A **production** environment gets its configuration from the provisioned secret store and config map — generated secrets and connection strings, never a hand-edited file.

That contract only holds if both sides stay in lockstep with the code. **Any PR that adds a new environment variable the application reads must update both the dev template and the production provisioning, in the same PR.**

## Rules

- **Document the variable in the dev template.** A short comment above it states what the value is for, the expected format, the safe default for local development (if any), and **what happens if it's missing**. Group it under an existing section header when it fits, or open a new one.

- **Provision the variable for real deploys.** Which path depends on what kind of value it is:

  - **Boot-critical secret** — the application refuses to start (or refuses a feature) without it, and it is a value the operator cannot reasonably invent (encryption keys, signing keys, HMAC keys). **Generate it in the provisioning layer**, store it in the secret manager as the durable source of truth, and wire it into the runtime's secret set.
    **Keep generated secrets stable in state — do not regenerate on re-apply.** Rotating a token-signing secret invalidates every live session; changing a data-encryption key after rows are encrypted is **data loss**.
  - **Non-secret production config** (a URL, a tunable, a limit) — add it to the config map, or use the provisioning layer's documented escape hatch for extra config values.
  - **Operator-supplied secret** (a third-party API key the operator pastes in) — document it in the dev template, and in production feed it through the extra-secrets escape hatch. It is **not** generated by the provisioning layer. A feature gated on it should **fail fast at boot** when its flag is on but the value is missing or still a placeholder — mirror the existing boot guard rather than discovering it at first use.

  A variable that meets none of these bars (an optional integration URL with a safe default) needs only the dev-template entry — the operator opts in.

- **Add a boot guard for anything genuinely required.** The application should refuse to start in production with a missing or placeholder value, and say which variable and why. A silent insecure default is worse than a failed boot.

- **Note the rotation policy in the comment** when it matters. State whether the value is safe to rotate (it only invalidates short-lived URLs) or must never change once data depends on it.

- **Note that a running deployment re-reads configuration only at start.** After changing a production secret or config value, the workloads need a restart/rollout — say so in the PR if it isn't obvious.

- **Never commit a real value.** The template carries placeholders only. Verify with a secret scan before pushing; if a real credential ever lands in history, rotating it is the fix, not deleting the line.

## Reviewer checklist

A PR that adds a new environment variable without updating **both** the dev template and the production provisioning (when applicable) is **incomplete** and should be rejected — either a fresh dev environment is missing the documented entry, or the next production deploy fails to boot or silently runs with an insecure default.

1. The template entry exists, with a comment: purpose, format, dev default, failure mode.
2. The production path is chosen deliberately (generated secret / config map / operator-supplied) and wired.
3. Anything required has a boot guard.
4. Rotation policy noted where it matters; restart requirement noted where it applies.
5. No real values in the diff.
